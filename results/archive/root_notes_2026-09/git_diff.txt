+# Design Notes: Prefill Double Buffering in llama.cpp
+
+## 1. Goal
+
+Validate whether a large MoE prefill can keep only two complete transformer layers in VRAM and overlap transfer of the next layer with computation of the current layer.
+
+The target experiment is a CUDA decoder-only MoE model, using a large prefill ubatch, normally capped at 4096 tokens. Each slot contains every weight needed by one layer, including all MoE experts, shared experts, biases, and scale tensors used by that layer.
+
+The desired steady state is:
+
+```text
+Host RAM:     full model weights
+VRAM slot 0:  layer il       <-> compute
+VRAM slot 1:  layer il + 1   <-> transfer
+
+then alternate the slots
+```
+
+Generation remains on the existing execution path. It is acceptable for generation to keep experts on CPU or otherwise use the normal scheduler. This work validates prefill first.
+
+## 2. Important API and Architecture Corrections
+
+The supplied design notes identify the right two implementation directions, but several details must match this checkout.
+
+### 2.1 Custom operations
+
+The public API is `ggml_map_custom1` or `ggml_map_custom1_inplace`, not `ggml_custom1`:
+
+```c
+struct ggml_tensor * ggml_map_custom1(
+        struct ggml_context * ctx,
+        struct ggml_tensor  * a,
+        ggml_custom1_op_t     fun,
+        int                   n_tasks,
+        void                * userdata);
+```
+
+The callback signature is:
+
+```c
+void callback(
+    struct ggml_tensor * dst,
+    const struct ggml_tensor * src,
+    int ith,
+    int nth,
+    void * userdata);
+```
+
+`MAP_CUSTOM1` is implemented by the CPU backend in the current source. It is not a CUDA kernel that can be inserted into a CUDA stream and is not automatically a general host callback from a CUDA graph. If the scheduler places this operation on CPU, the existing scheduler dependency/copy machinery must be allowed to synchronize the relevant data before the callback runs.
+
+Therefore a custom operation is useful for a correctness probe, but it is not the final overlap mechanism. The callback must also be safe when called with multiple tasks. Use `n_tasks = 1` for a synchronization probe, and ensure the callback is not invoked more than once per graph execution.
+
+### 2.2 Backend events and asynchronous uploads
+
+This checkout exposes:
+
+- `ggml_backend_graph_compute_async`
+- `ggml_backend_tensor_set_async`
+- `ggml_backend_tensor_copy_async`
+- `ggml_backend_event_new`
+- `ggml_backend_event_record`
+- `ggml_backend_event_synchronize`
+- `ggml_backend_event_wait`
+
+CUDA implements backend event record and wait with CUDA events and stream waits. The model loader already uses asynchronous tensor upload plus events for staging-buffer reuse. This existing infrastructure is the preferred foundation for the overlap prototype.
+
+The event API is backend-level, not a promise that every backend supports the same concurrent copy/compute behavior. The prototype must check the selected device and fall back when async upload or event ordering is unavailable.
+
+## 3. Core Design: Static Graph Weight Slots
+
+The central idea is valid only if the graph contains stable tensor objects whose storage points to fixed slot addresses:
+
+```text
+layer 0 weight tensor -> slot 0 storage
+layer 1 weight tensor -> slot 1 storage
+layer 2 weight tensor -> slot 0 storage
+layer 3 weight tensor -> slot 1 storage
+```
+
+The graph may therefore be built with alternating slot-backed tensors. At runtime, the host overwrites a slot with the next layer only after the GPU has finished all operations that read the previous contents.
+
+This is different from changing `ggml_tensor::data` while a graph is executing. Tensor metadata and backend allocation must remain stable for the lifetime of submitted work. The implementation must never mutate active tensor pointers or reuse a slot before its compute-complete event.
+
+The graph can be built up front only if the layer graphs are separate or if the graph has explicit synchronization nodes between layer regions. A full graph with alternating pointers does not by itself make host overwrites safe: the host still needs a precise ordering point before each slot is reused.
+
+## 4. Two Validation Approaches
+
+### Approach 1: CPU synchronization probe with `ggml_map_custom1`
+
+This is the smallest way to validate the overwrite protocol and tensor binding without first adding a new backend abstraction.
+
+At the end of each supported layer region, insert a CPU custom node that has the current activation as its input. The dependency ensures the node is after the layer's output. The callback can:
+
+1. Notify a transfer worker that the previous slot is no longer needed.
+2. Wait until the worker has finished preparing the next slot.
+3. Return the activation unchanged.
+
+Conceptually:
+
+```text
+layer N compute
+    |
+CPU MAP_CUSTOM1 synchronization node
+    |
+layer N + 1 compute
+```
+
+The callback should carry a small synchronization object in `userdata`, containing the layer index, slot index, condition variable, and failure state. Do not use global mutable state. Use one task for the callback.
+
+#### What this proves
+
+- The layer tensors can be represented by fixed slot-backed objects.
+- The host can overwrite a slot only after the prior layer has completed.
+- The complete MoE layer can be transferred without changing graph tensor shapes or kernel contracts.
+- The graph produces correct logits and KV-cache state.
+
+#### What this does not prove
+
+- CUDA compute and host-to-device transfer overlap.
+- That the custom node can execute inside a CUDA graph capture.
+- That the scheduler will place the custom node and its copies with the desired dependencies on every backend.
+- That a CPU callback has acceptable latency.
+
+A custom-node prototype should disable CUDA graph capture and use a normal scheduler path. It should log the backend assigned to the custom node. If the scheduler cannot produce a correct CPU split, stop using this approach and move to explicit graph chunking.
+
+The callback may introduce a pipeline bubble because CPU execution can require synchronization with preceding GPU work. That is acceptable for this validation stage.
+
+### Approach 2: Layer graphs with backend events
+
+This is the production-shaped design and the only approach that should be used to measure true transfer/compute overlap.
+
+Build one graph per transformer layer, or one reusable layer graph whose bound weight tensors alternate between two fixed slots. The CPU orchestrates transfers and graph submission while the backend streams enforce ordering:
+
+```text
+transfer layer 0 -> slot 0
+record upload_done[0]
+
+compute layer 0 waits for upload_done[0]
+transfer layer 1 -> slot 1 while layer 0 computes
+record upload_done[1]
+
+compute layer 1 waits for upload_done[1]
+transfer layer 2 waits for compute_done[0], then writes slot 0
+```
+
+The important ordering is:
+
+```text
+upload(layer il, slot s)
+    -> upload_done[s]
+    -> compute(il) waits on upload_done[s]
+    -> compute_done[s]
+    -> next upload using slot s waits on compute_done[s]
+```
+
+The CPU should not call `ggml_backend_event_synchronize` in the steady-state path except during teardown, error handling, or a required staging-buffer reuse. GPU-side `ggml_backend_event_wait` should establish the dependency on the compute backend.
+
+## 5. Recommended Implementation Sequence
+
+### Stage 0: Instrument the existing path
+
+Measure before changing execution:
+
+- Per-layer tensor byte sizes, including all MoE experts.
+- Largest layer and required slot size.
+- Existing model host and device buffer sizes.
+- Per-layer compute time for 1024, 2048, and 4096 tokens.
+- Existing model-load upload behavior and whether the selected CUDA buffer type supports async upload.
+- Free VRAM before and after model load.
+
+This validates the memory assumption and establishes whether layer compute is long enough to hide transfer.
+
+### Stage 1: Static slot and synchronous copy proof
+
+Use one supported CUDA architecture and one slot first.
+
+1. Keep a canonical host copy of all model tensors.
+2. Allocate one device buffer large enough for the largest supported layer.
+3. Create slot-backed tensor views with the original type, shape, strides, quantization layout, and alignment.
+4. Copy one complete layer into the slot synchronously.
+5. Build and execute one layer graph.
+6. Pass its activation and memory context to the next layer.
+7. Compare logits and subsequent generation with normal execution.
+
+This stage intentionally avoids custom callbacks, a second slot, and asynchronous copies. It establishes that graph decomposition and binding are correct.
+
+### Stage 2: Custom-node synchronization probe
+
+If the static binding works, add `ggml_map_custom1` only as a development probe for the slot handoff.
+
+The probe may use two slots and a background transfer thread, but it should initially use synchronous or explicitly completed transfers. Its purpose is to demonstrate that the graph reaches a safe per-layer handoff and that the next layer observes the new slot contents.
+
+Do not treat this stage as a benchmark. Disable CUDA graph capture, keep the callback single-task, and retain a normal-path fallback.
+
+### Stage 3: Two-slot asynchronous overlap
+
+Replace the CPU callback protocol with explicit layer-graph submission and backend events:
+
+1. Allocate slot 0 and slot 1 from the selected CUDA device buffer type.
+2. Build a layer manifest describing every tensor's slot offset and byte size.
+3. Create upload-complete and compute-complete events for both slots.
+4. Start upload of layer 0 into slot 0.
+5. Record `upload_done[0]` on completion of that upload stream.
+6. Submit layer 0 with `ggml_backend_event_wait(compute_backend, upload_done[0])`.
+7. Start upload of layer 1 into slot 1.
+8. Before reusing slot 0 for layer 2, make its upload stream wait for `compute_done[0]`.
+9. Continue alternating slots.
+
+The exact upload backend may be the existing model upload backend or a dedicated backend context, but it must be a backend-supported stream. Do not call CUDA stream APIs directly from llama.cpp.
+
+## 6. Layer Graph and Activation Ownership
+
+The current full graph is built through `llama_model::build_graph` and architecture-specific graph builders. It is not safe to insert host-side slot reuse merely because the source code has a loop over layers.
+
+The layer execution unit must include the complete transformer layer:
+
+- Attention projections and attention.
+- KV-cache writes for that layer.
+- Routing and all selected MoE operations.
+- Every expert tensor needed by the MoE operation.
+- Residual and normalization operations.
+
+The output activation becomes the input to the next layer graph. It must remain in normal backend compute memory and must not alias a slot that is being overwritten.
+
+The layer graph builder should accept:
+
+- Layer index.
+- Current activation.
+- Existing ubatch and position inputs.
+- Existing memory context.
+- An explicit bound-layer tensor view.
+- A final-layer/output flag.
+
+The first architecture should be implemented by factoring or adapting its existing layer loop. Do not refactor every architecture before the first result.
+
+The final output norm, output projection, pooling, and sampling must be handled as a separate final stage where the architecture requires it.
+
+## 7. Layer Slot Representation
+
+Do not initially create a universal packed format. Create an internal manifest for one architecture that records:
+
+- Layer index.
+- Tensor identity and name.
+- Host source tensor or source address.
+- Slot offset.
+- Tensor byte size.
+- Tensor type, dimensions, and strides.
+- Alignment and backend buffer type.
+
+Slot size is the maximum layer allocation rounded using the actual backend buffer alignment. Do not assume 256-byte alignment without querying the buffer/backend contract.
+
+A slot-backed tensor must preserve the original quantized representation. This is especially important for `GGML_OP_MUL_MAT_ID`, which expects a particular expert tensor layout. If a tensor cannot be represented as a valid view, disable the prototype for that architecture rather than silently repacking it.
+
+Do not mutate canonical `llama_layer` pointers globally. Use an explicit layer view or binding passed to the selected graph builder. This keeps the normal full-graph path and fallback path independent.
+
+## 8. Host-to-Device Transfer
+
+The model loader demonstrates an existing pattern for asynchronous upload:
+
+```text
+read or obtain host data
+wait before reusing a staging buffer
+set tensor asynchronously
+record an event
+reuse the staging buffer only after its event completes
+```
+
+Reuse that infrastructure where possible. The transfer source must be valid for the selected async API. Mmap-backed data may need pinned staging memory; do not assume every mmap mapping can be registered directly.
+
+For the first async prototype:
+
+- Use a bounded number of pinned staging buffers.
+- Record an upload event after each slot upload.
+- Wait for that event before reusing the staging buffer.
+- Report synchronous-copy fallback clearly.
+- Keep host memory lifetime longer than all pending uploads.
+
+If asynchronous host upload is unavailable, retain the synchronous validation path and do not claim overlap.
+
+## 9. Scheduler and Backend Boundaries
+
+The custom-node proof may use the existing scheduler, but the true overlap path should avoid hiding cross-stream work inside a full scheduler submission.
+
+A suitable boundary is:
+
+```text
+llama.cpp layer executor:
+    chooses layer and slot
+    builds or reuses layer graph
+    submits upload and compute dependencies
+    owns activation handoff
+
+backend API:
+    owns streams, events, copies, and synchronization
+```
+
+Stage 1 may call the existing scheduler once per layer. Stage 3 may require a small backend-neutral helper around event and async-copy operations, but it should reuse the existing `ggml_backend_*` APIs first. Do not add CUDA types to `llama_context`.
+
+Every backend capability must be checked. CUDA is the only target for this experiment; all other backends use the normal path.
+
+## 10. MoE Behavior
+
+The complete layer transfer includes:
+
+- Gate/router weights.
+- All expert up, gate, and down weights.
+- Expert biases and scale tensors.
+- Shared expert tensors.
+- Any architecture-specific latent or fused expert tensors.
+
+The graph continues to perform normal routing and top-k selection. There is no host-side expert-selection barrier in the current graph model. The synchronization boundary is after the complete layer graph, not after routing.
+
+For a 4096-token prefill, whole-layer transfer is a reasonable first hypothesis because many experts may be active. The benchmark must still measure transfer size and compute time rather than assume all experts are equally useful.
+
+## 11. Correctness Tests
+
+Compare normal and streamed execution using the same model, prompt, context parameters, and seed:
+
+- Prompt logits for all requested outputs.
+- First generated token.
+- Several later generated tokens.
+- Continued generation after streamed KV-cache writes.
+- Prompt sizes below and above the threshold.
+- 1024, 2048, and 4096-token cases where supported.
+- Quantized MoE tensors and per-expert scales.
+- Single sequence first; multiple sequences later.
+- Context reuse only after the basic path works.
+
+Classify mismatches as binding/layout, activation handoff, KV-cache ordering, final-stage handling, or normal backend nondeterminism.
+
+## 12. Performance Measurements
+
+The custom-node path is a correctness probe and may be slower because the CPU callback can force a synchronization bubble.
+
+For the event path, report:
+
+- End-to-end prefill tokens per second.
+- Layer upload time.
+- Layer compute time.
+- Upload/compute overlap.
+- Slot reuse stalls.
+- Graph build and scheduler allocation time.
+- Peak VRAM.
+- Host memory bandwidth.
+- Generation speed after streamed prefill.
+
+The event path is worthwhile only if it reduces end-to-end prefill time and reduces model-weight VRAM residency. Overlap measured only at the copy API is insufficient if graph construction dominates.
+
+## 13. Failure and Fallback Rules
+
+Use the existing full-graph path when:
+
+- The backend is not the supported CUDA device.
+- The model architecture is not explicitly supported.
+- A layer does not fit in the slot budget.
+- A tensor has incompatible layout, alignment, or buffer type.
+- Async upload or events are unavailable.
+- A custom-node or layer-graph allocation fails.
+- An unsupported memory, adapter, recurrent, encoder, hybrid, or cross-attention path is active.
+- The request is generation-sized or below the configured prefill threshold.
+
+Fallback must happen before modifying active model tensor ownership. A failed experiment must not leave the normal model path pointing at a temporary slot.
+
+## 14. Acceptance Criteria
+
+The first validation is successful when:
+
+1. One supported CUDA MoE architecture runs prefill with static slot-backed weights.
+2. The custom-node probe, if used, completes without slot corruption.
+3. Streamed logits match normal execution within expected tolerance.
+4. Generation after streamed prefill remains correct.
+5. The normal path remains unchanged for unsupported cases.
+6. The event-based two-slot version demonstrates measurable copy/compute overlap.
+7. End-to-end prefill improves enough to justify the additional synchronization code.
+
+The contribution boundary should be:
+
+```text
+first change: static layer binding and correctness proof
+next change:  custom-node synchronization probe if useful
+main feature: two-slot layer graphs with backend events
+later work:   broader architectures, backends, generation caching, and multi-GPU support
+```
+
+## 14. Implementation Hand-off and Review Status
+
+### Completed
+
+- Added the opt-in `prefill_streaming` context flag.
+- Added `llama-bench` support for `--prefill` and `--prefill-streaming`.
+- Added `DBPREFILL:` diagnostics and timing reports.
+- Added model layer-size reporting.
+- Added a two-slot allocation and layer packing prototype.
+- Added Qwen3-MoE and DeepSeek2 tensor-binding scaffolding.
+- Added direct host-pointer slot writes where source tensors are host-backed.
+- Added one reusable staging buffer for non-host source tensors.
+- Disabled full-graph slot binding and automatic slot filling after review found that they were unsafe before graph chunking.
+
+### Critical review result
+
+The earlier full-graph slot experiment was invalid. It filled slot 0 with layers 0, 2, 4, ... and slot 1 with layers 1, 3, 5, ... before submitting one graph. The graph then referenced the same slot for multiple distinct layers. Earlier layers therefore observed overwritten data. Its reported throughput must not be used as a correctness or performance result.
+
+Two slots are allocated once per context. The old fill loop did not allocate or clear the slots per layer, but it did allocate a temporary `std::vector<uint8_t>` for every tensor and perform a backend read followed by a backend write. That path is now disabled until layer execution is chunked.
+
+### Valid baseline
+
+Using the Qwen3-Coder 30B-A3B model with `-ngl 0`, `-ub 2048`, `-p 1024`, `-n 0`, and `-lm none`:
+
+```text
+-ncmoe 40: 77.72 t/s
+-ncmoe 48: 78.34 t/s
+```
+
+The difference is within normal run-to-run noise for this single-repetition measurement. `-ncmoe N` places expert tensors for layers `0` through `N - 1` on CPU; it is not an expert-count setting. For this 48-layer model, `-ncmoe 48` is the complete expert-on-CPU configuration.
+
+### Next required implementation
+
+The actual feature still requires a layer executor. The next change must:
+
+1. Build a graph for one transformer layer only.
+2. Execute that graph before reusing its slot.
+3. Carry the resulting activation and KV-cache state into the next layer graph.
+4. Fill only the slot needed for the next layer.
+5. Add upload and compute events after synchronous correctness works.
+
+The existing full-graph binding callback should not be re-enabled. A first implementation should target Qwen3-MoE only, use a host activation bridge if necessary for correctness, and compare its logits against the normal scheduler before optimizing the bridge or adding asynchronous overlap.

+bool llama_context::init_prefill_streaming_slots() {
+    if (dbprefill_slots.size() == 2) {
+        return true;
+    }
+
+    ggml_backend_t backend = nullptr;
+    for (const auto & candidate : backends) {
+        auto * device = ggml_backend_get_device(candidate.get());
+        if (ggml_backend_dev_type(device) == GGML_BACKEND_DEVICE_TYPE_GPU) {
+            backend = candidate.get();
+            break;
+        }
+    }
+
+    if (!backend) {
+        LLAMA_LOG_INFO("DBPREFILL: slot_fill disabled reason=no_gpu_backend\n");
+        return false;
+    }
+
+    const int64_t start_us = ggml_time_us();
+    const auto buft = ggml_backend_get_default_buffer_type(backend);
+    const size_t alignment = ggml_backend_buft_get_alignment(buft);
+    size_t largest_layer = 0;
+    for (uint32_t il = 0; il < model.hparams.n_layer_all; ++il) {
+        size_t layer_size = 0;
+        for (const auto * tensor : model.get_prefill_streaming_layer_tensors(il)) {
+            layer_size = (layer_size + alignment - 1) / alignment * alignment;
+            layer_size += ggml_nbytes(tensor);
+        }
+        largest_layer = std::max(largest_layer, layer_size);
+    }
+    largest_layer = (largest_layer + alignment - 1) / alignment * alignment;
+
+    dbprefill_slots.resize(2);
+    dbprefill_layer_offsets.resize(model.hparams.n_layer_all);
+    for (int slot = 0; slot < 2; ++slot) {
+        ggml_init_params params = {
+            /*.mem_size   =*/ ggml_tensor_overhead(),
+            /*.mem_buffer =*/ nullptr,
+            /*.no_alloc   =*/ true,
+        };
+        dbprefill_slots[slot].ctx.reset(ggml_init(params));
+        dbprefill_slots[slot].tensor = dbprefill_slots[slot].ctx
+            ? ggml_new_tensor_1d(dbprefill_slots[slot].ctx.get(), GGML_TYPE_I8, largest_layer)
+            : nullptr;
+        dbprefill_slots[slot].buffer.reset(dbprefill_slots[slot].ctx && dbprefill_slots[slot].tensor
+            ? ggml_backend_alloc_ctx_tensors(dbprefill_slots[slot].ctx.get(), backend)
+            : nullptr);
+        if (!dbprefill_slots[slot].ctx || !dbprefill_slots[slot].tensor || !dbprefill_slots[slot].buffer) {
+            dbprefill_slots.clear();
+            LLAMA_LOG_INFO("DBPREFILL: slot_fill disabled reason=slot_initialization_failed\n");
+            return false;
+        }
+        ggml_backend_buffer_set_usage(dbprefill_slots[slot].buffer.get(), GGML_BACKEND_BUFFER_USAGE_WEIGHTS);
+        dbprefill_slots[slot].size = largest_layer;
+    }
+
+    LLAMA_LOG_INFO("DBPREFILL: slots allocated count=2 bytes_each=%zu alignment=%zu\n", largest_layer, alignment);
+    dbprefill_timing_data.slot_init_us += ggml_time_us() - start_us;
+    return true;

+bool llama_context::fill_prefill_streaming_slot(int slot, int il) {
+    if (slot < 0 || slot >= (int) dbprefill_slots.size()) {
+        return false;
+    }
+
+    auto & dst = dbprefill_slots[slot];
+    const auto tensors = model.get_prefill_streaming_layer_tensors(il);
+    const size_t alignment = ggml_backend_buffer_get_alignment(dst.buffer.get());
+    const int64_t fill_start_us = ggml_time_us();
+    size_t offset = 0;
+    for (const auto * source : tensors) {
+        const size_t size = ggml_nbytes(source);
+        offset = (offset + alignment - 1) / alignment * alignment;
+        if (offset + size > dst.size) {
+            return false;

+void llama_model::log_prefill_streaming_diagnostics(uint32_t n_tokens) const {
+    std::vector<size_t> layer_bytes(hparams.n_layer_all, 0);
+    size_t non_layer_bytes = 0;
+
+    for (const auto & [name, tensor] : tensors_by_name) {
+        const std::string prefix = "blk.";
+        const size_t prefix_pos = name.find(prefix);
+        if (prefix_pos == std::string::npos) {
+            non_layer_bytes += ggml_nbytes(tensor);
+            continue;
+        }
+
+        size_t pos = prefix_pos + prefix.size();
+        size_t layer = 0;
+        while (pos < name.size() && name[pos] >= '0' && name[pos] <= '9') {
+            layer = layer * 10 + (name[pos] - '0');
+            ++pos;
+        }
+
+        if (pos == prefix_pos + prefix.size() || layer >= layer_bytes.size()) {
+            non_layer_bytes += ggml_nbytes(tensor);
+            continue;
+        }
+
+        layer_bytes[layer] += ggml_nbytes(tensor);
+    }
+
+    size_t largest_layer = 0;
+    size_t total_layer_bytes = 0;
+    for (size_t il = 0; il < layer_bytes.size(); ++il) {
+        total_layer_bytes += layer_bytes[il];
+        largest_layer = std::max(largest_layer, layer_bytes[il]);
+        LLAMA_LOG_INFO("DBPREFILL: layer=%zu bytes=%zu MiB=%.2f\n",
+                il, layer_bytes[il], layer_bytes[il] / 1024.0 / 1024.0);
+    }
+
+    const bool large_prefill = n_tokens >= 1024;
+    LLAMA_LOG_INFO("DBPREFILL: tokens=%u threshold=1024 eligible=%s\n",
+            n_tokens, large_prefill ? "yes" : "no");
+    LLAMA_LOG_INFO("DBPREFILL: layers=%zu largest_layer_bytes=%zu largest_layer_mib=%.2f total_layer_mib=%.2f non_layer_mib=%.2f\n",
+            layer_bytes.size(), largest_layer, largest_layer / 1024.0 / 1024.0,
+            total_layer_bytes / 1024.0 / 1024.0, non_layer_bytes / 1024.0 / 1024.0);
